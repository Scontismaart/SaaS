# Pre-release secret rotation

**Gate:** `RELEASE SECRET ROTATION = REQUIRED`

**Status:** Not performed during database hardening.
**Rule:** Never put secret values in Git, command history, generated manifests, or reports. Update secrets through the relevant secret store and provider dashboard.

This inventory is based on `.env.example`, `.env.production.example`, and the current server-side consumers in `src/`. Before release, compare it with the actual deployment secret store and provider consoles; templates do not prove which optional integrations are enabled.

## Safe rotation order

1. Inventory active deployments, workers, scheduled jobs, CI, local tools, provider webhooks, and tenant integrations. Record the secret name, owner, consumer, change window, and a verification result without recording its value.
2. Create and verify a fresh main backup and a staging restore before changing database or encryption credentials. Keep rollback access available through the secret manager.
3. Rotate provider credentials one integration at a time. Where the provider supports overlap, add the new credential, update the deployment, restart consumers, run the verification above, and then revoke the old credential.
4. Handle `ENCRYPTION_KEY` only with a separately reviewed dual-key/re-encryption release. Preserve the old key until every database ciphertext has been re-encrypted and verified.
5. Rotate Supabase Auth signing material and privileged API keys in a planned window. Update every server consumer, never the browser; expect signing-key changes to invalidate sessions and require reauthentication.
6. Rotate the Supabase database password after preparing every consumer (`DATABASE_URL`, verification/backup URLs, API, scheduler and recovery tooling). Reset it in Supabase, update the secret store immediately, restart all pools, then verify health, read-only access, backup and restore connectivity before ending the window.
7. Run the release preflight, webhook and provider smoke checks, database health checks, secret scanning, and a final log/bundle review. Confirm old credentials are revoked and no value was written to source, artifacts, shell history, or reports.

Do not combine multiple provider rotations in one release window. If any verification fails, stop and restore the last known-good deployment secret configuration before revoking another credential.
